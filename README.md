# Система учёта парка кикшеринга «ВышКат» («Доедем до дедлайна»)

Консольное приложение и доменная модель для автоматизации инвентарного учёта транспорта и оборудования сервиса кикшеринга «ВышКат» с применением принципов SOLID, собственного легковесного DI-контейнера и модульных тестов.

---

## 1. Архитектура и логика решений

Проект разделён на три независимых пакета без избыточных прослоек:

* **`domain/`** — ядро предметной области:
  * `interfaces.py`: базовые контракты `IInventoryItem` (объекты инвентарного учёта), `IEnergyConsumer` (потребители электроэнергии) и `IServiceCenter` (сервис техосмотра).
  * `vehicles.py`: иерархия транспорта (`Vehicle` -> `ElectricVehicle` -> `KickScooter`, `ElectricBike`, а также не потребляющий электроэнергию `MechanicalBike`).
  * `equipment.py`: иерархия инвентарных вещей на балансе (`Equipment` -> `Helmet`, `ChargingStation`).
* **`services/`** — бизнес-логика и инфраструктура DI:
  * `service_center.py`: стандартная реализация техосмотра (`DefaultServiceCenter`).
  * `fleet_manager.py`: сервис учёта парка (`FleetManager`), отвечающий за приёмку транспорта через техосмотр, учёт вещей, расчёт энергопотребления и отбор техники для новичков.
  * `container.py`: легковесный DI-контейнер (`DIContainer`), разрешающий зависимости через анализ аннотаций типов конструктора (`get_type_hints`).
* **`tests/`** — юнит-тесты поведения (`test_vyshkat.py`) с подменой сервиса техосмотра через Stub-классы и `MagicMock`.

## 2. Применение принципов SOLID

* **S — Single Responsibility Principle (Принцип единственной ответственности):**
  * Доменные классы (`KickScooter`, `MechanicalBike`, `Helmet`, `ChargingStation`) отвечают только за хранение инвариантов и валидацию собственных атрибутов при создании.
  * `DefaultServiceCenter` отвечает исключительно за логику технического допуска транспорта.
  * `DIContainer` отвечает только за регистрацию и создание графа зависимостей.
* **O — Open/Closed Principle (Принцип открытости/закрытости):**
  * Сервис `FleetManager` работает с абстракциями `IInventoryItem`, `IEnergyConsumer`, `Vehicle` и `Equipment`. Добавление новых видов транспорта или инвентаря не требует изменения кода `FleetManager` или `DefaultServiceCenter`.
* **L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков):**
  * Любой подкласс `Vehicle` (`KickScooter`, `ElectricBike`, `MechanicalBike`) корректно заменяет базовый тип при прохождении техосмотра и фильтрации для новичков. Механический велосипед (`MechanicalBike`) выделен в отдельную ветку от `ElectricVehicle`, поэтому он не нарушает контракт потребителя энергии фиктивным возвратом `0` или выбросом исключений.
* **I — Interface Segregation Principle (Принцип разделения интерфейса):**
  * Вместо единого «толстого» интерфейса введены узкие контракты `IInventoryItem` и `IEnergyConsumer`. Шлемы и механические велосипеды не обязаны реализовывать свойство расхода энергии (`daily_energy_kwh`), а зарядные станции (`ChargingStation`) реализуют `IEnergyConsumer`, не будучи транспортными средствами.
* **D — Dependency Inversion Principle (Принцип инверсии зависимостей):**
  * Модуль верхнего уровня `FleetManager` не зависит от конкретного класса `DefaultServiceCenter` — он принимает в конструкторе абстракцию `IServiceCenter`, которая внедряется через `DIContainer`.

## 3. Ответы на обязательные вопросы

### 1) Какой принцип SOLID применён наиболее явно и где?
Наиболее явно применены два принципа:
* **ISP (`domain/interfaces.py`, `domain/vehicles.py`, `domain/equipment.py`):** разделение интерфейсов `IInventoryItem` и `IEnergyConsumer` позволило перекрёстно комбинировать свойства объектов разных иерархий. Например, `ChargingStation` (наследник `Equipment`) и `KickScooter` (наследник `Vehicle`) оба реализуют `IEnergyConsumer` и полиморфно учитываются в `FleetManager.get_total_daily_energy_kwh()`, тогда как `MechanicalBike` и `Helmet` реализуют только `IInventoryItem`.
* **DIP (`services/fleet_manager.py`, `services/container.py`):** `FleetManager.__init__` зависит от интерфейса `IServiceCenter`, а связывание абстракции с конкретной реализацией происходит во внешнем `DIContainer`.

### 2) Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?
Сознательно ограничен **SRP (принцип единственной ответственности)** в классе **`FleetManager`** (`services/fleet_manager.py`):
* Этот класс одновременно управляет бизнес-процессом приёмки техники, хранит коллекцию объектов в памяти (`self._inventory: List[IInventoryItem]`) и формирует аналитические выборки (расчёт суммарной энергии `get_total_daily_energy_kwh()` и фильтрация для новичков `get_novice_friendly_vehicles()`).
* **Почему это приемлемо:** выделение отдельных интерфейсов и классов `IInventoryRepository`, `IEnergyReportService` и `INoviceFilterService` для небольшого консольного приложения без базы данных привело бы к неоправданному усложнению архитектуры (overengineering) и появлению классов-обёрток из двух строк кода.

### 3) Что сломается (или не сломается) при добавлении нового вида транспорта, сотрудника или склада запчастей?
* **Новый вид транспорта (например, моноколесо `Monowheel(ElectricVehicle)` в `domain/vehicles.py`):** ничего не сломается (соблюдается **OCP**). `FleetManager` автоматически примет его через `try_add_vehicle()`, учтёт энергопотребление через `IEnergyConsumer` и проверит рейтинг простоты для новичков.
* **Сотрудник службы эксплуатации (`Employee`):** ничего не сломается. По условиям предметной области сотрудники не ставятся на инвентарный баланс, поэтому класс `Employee` не будет реализовывать `IInventoryItem` и не попадёт в реестр имущества. При необходимости его можно задействовать внутри новой реализации `IServiceCenter` без изменения сигнатур `FleetManager`.
* **Склад запчастей (`SparePartsWarehouse`):** существующий код не сломается. Если запчасти требуют инвентарного учёта, достаточно унаследовать класс `SparePart` от `Equipment` (`IInventoryItem`), и он сразу будет поддерживаться методом `add_equipment()`. Если для склада потребуется отдельный учёт остатков по артикулам, это будет новый сервис, не ломающий работу `FleetManager`.

### 4) Какой тест фиксирует решение техосмотра и/или правило «для новичков»; как подменяется зависимость?
Все тесты расположены в модуле `tests/test_vyshkat.py` (класс `TestVyshKatFleet`):
* **Решение техосмотра и подмена зависимости:**
  * `test_accepts_sound_vehicle_and_rejects_faulty_one` — проверяет базовую работу `DefaultServiceCenter`.
  * `test_di_substitution_with_stub_service_center` — демонстрирует подмену зависимости в DI-контейнере через `container.register(IServiceCenter, AlwaysRejectServiceCenterStub)` и `AlwaysApproveServiceCenterStub`, доказывая, что решение о приёмке в `FleetManager` полностью определяется внедрённой реализацией `IServiceCenter`.
  * `test_di_substitution_with_magic_mock` — подменяет сервис техосмотра на `unittest.mock.MagicMock(spec=IServiceCenter)` через `container.register_instance(...)` и проверяет факт вызова `inspect()` с конкретным экземпляром транспорта.
* **Правило «для новичков» (простота >= 6):**
  * `test_novice_friendly_vehicles_filtering` — проверяет граничные значения оценки простоты (`5`, `6`, `9`) и фиксирует, что метод `get_novice_friendly_vehicles()` возвращает только транспорт с рейтингом `>= 6`.

### 5) Что сделал ИИ, а что изменили вы?
* **Роль ИИ-помощника:** Помощь в проектировании структуры пакетов (`domain`, `services`, `tests`), в выявлении допущенных ошибок в коде. Тесты полностью написал ИИ.
* **Что сделано и переработано самостоятельно:**
  * Выбор стека на чистой стандартной библиотеке Python (`abc`, `typing`, `unittest`) без сторонних зависимостей для гарантированной воспроизводимости сборки;
  * Адаптация кода под совместимость с Python 3.9+ (`from __future__ import annotations`);
  * Проработка разграничения иерархий `ElectricVehicle` / `MechanicalBike` и `Helmet` / `ChargingStation` для демонстрации работы принципов ISP и LSP;
  * Настройка окружения, запуск, верификация тестовых сценариев и проверка граничных случаев валидации.

## 4. Инструкция по запуску

Проект использует только стандартную библиотеку Python (версии 3.9 и выше), установка внешних пакетов не требуется.

**Запуск демонстрационного сценария консольного приложения:**
```bash
python3 main.py
```

**Запуск модульных тестов:**
```bash
python3 -m unittest discover -s tests -v
```
